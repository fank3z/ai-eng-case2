# Кейс 2 — RAG на базі знань NOC + evals у CI

Другий зріз курсового проєкту *AI-асистент інженера NOC / інтеграції сайтів*.
Блок 1 витягував структуру з тікетів; тут — RAG, що відповідає на питання інженера за регламентами,
каталогами аварій і настановами, **з посиланням на документ і розділ** і чесним «у документах цього немає».

```
data/raw (MD/HTML/DOCX/PDF) → loaders (структура) → очищення → дедуплікація → chunking + метадані
  → embeddings (fastembed, локально) → FAISS  ┐
  → BM25                                      ┴→ RRF → reranker (cross-encoder) → фільтри
  → бюджет контексту → Gemini (structured output: answer + claims[sources]) → відповідь з джерелами
  → evals: retrieval (recall@k, MRR) + відповіді (детерміновані, LLM-judge з калібруванням, faithfulness) → CI
```

## Запуск

```bash
make setup                 # pip install -r requirements.txt  (Python 3.10+)
cp .env.example .env       # вписати GEMINI_API_KEY (aistudio.google.com → Get API key, free tier)
make run                   # = python main.py all
```
`make run`: ingestion → індекси → retrieval-evals → RAG-evals для промптів v1 і v2 → калібрування судді → таблиці в `REPORT.md`.
Перший запуск завантажує локальні моделі (~1.3 ГБ у `.models/`) і робить ~150 запитів до Gemini (тротлінг 1 запит / 7 с під free tier, ~20 хв).
Повторні запуски беруть відповіді з кешу `.cache/`.

| Команда | Що робить |
|---|---|
| `make ask Q="Скільки триває зміна NOC?"` | одне питання, відповідь з джерелами |
| `make search Q="..."` | лише пошук (видно ранги BM25 / vector / rerank) |
| `make smoke` | весь пайплайн без моделей і ключа (TF-IDF + mock LLM) — перевірка, що код працює |
| `make label` → розмітити → `make calibrate` | калібрування LLM-судді на ручній розмітці |
| `make ci` | те, що виконує GitHub Actions |

## Корпус (`data/`)
34 файли: **11 MD, 9 HTML, 8 DOCX, 6 PDF** → після дедуплікації **32 унікальні документи**.
База знань NOC вигаданого оператора *NetCo*: SOP з аварій, політики (пріоритети, ескалація, виїзди, зміни),
каталоги аварій, настанови (NB-IoT, PTP), стандарти, звіт. **Корпус синтетичний**: усі значення вигадані,
персональних і реальних мережевих даних немає (генератор — `tools/build_corpus.py`, джерела — `tools/corpus_src/`).

Навмисно закладені складнощі:
- **«бруд»**: навігація, cookie-банер, скрипти й футер у HTML; колонтитули й номери сторінок у DOCX/PDF;
  HTML у кодуванні windows-1251; багатосторінкові PDF з таблицями;
- **дублікати**: точна копія (`sop-vswr (копія).md`) і майже-дублікат (`faq-noc-archive.html`);
- **пастки**: скасовані версії (NB-IoT v1 → v2, стандарт резервного живлення 2023 → 2026), схожі документи
  (два каталоги аварій, кілька «72 годин» / «4 годин» у різних контекстах), документи з обмеженим доступом (менеджмент).

`data/processed/manifest.json` — по кожному файлу: формат, версія, дата, статус, доступ, хеш змісту, кількість чанків,
`duplicate_of` і причина. `data/processed/chunks.jsonl` — основні чанки, `chunks_fixed.jsonl` — baseline для порівняння.

## Ingestion
- **Структура**: усі формати приводяться до markdown (`#` заголовки, `-`/`1.` списки, `|` таблиці).
  DOCX — стилі Heading/List + таблиці в порядку документа; HTML — `article/main` без boilerplate;
  PDF — заголовки за розміром шрифту, таблиці через `find_tables`, склеювання переносів.
- **Очищення**: NFC, невидимі символи й м'які переноси, уніфікація апострофів (`’ʼ` → `'`, важливо для BM25),
  колонтитули (зона сторінки + повтор на ≥50% сторінок), номери сторінок, ©.
- **Дедуплікація**: SHA-256 нормалізованого змісту (точні дублікати навіть з різною розміткою) +
  Jaccard 5-шинглів ≥ 0.85 (майже-дублікати). Лишається новіша версія.

## Chunking: чому так
**Обрано structure-aware chunking: один розділ документа = один чанк.**
- Документи — регламенти з короткими розділами (30–150 токенів), і **відповідь майже завжди живе в одному розділі**
  («Порогові значення», «Коли потрібен виїзд»). Розділ — природна одиниця змісту і цитування («документ і розділ»).
- **Таблиці не ріжуться** (пороги, коди аварій, параметри NB-IoT — головні факти корпусу); рядок без шапки втрачає сенс.
  Якщо таблиця більша за ліміт, вона ділиться по рядках з повтором шапки.
- **Верхня межа 300 токенів** — більший розділ ділиться по межах абзаців/списків; **нижня межа 60** — дрібні
  розділи («Сфера дії» з одного речення) зливаються з наступним, щоб чанк мав контекст. У тексті злитого чанка
  збережено назви розділів `[Назва]`.
- **Contextual chunk header**: для BM25 і embeddings до чанка додається `Документ | Версія (чинна/СКАСОВАНА) | Розділ`
  — короткий розділ «Параметри» без цього не знайти за запитом «NB-IoT».

Порівняння з фіксованим вікном (50 слів ≈ 65 токенів, перекриття 12 — приблизно такий самий середній розмір),
повна таблиця з прикладами — `evals/results/chunking.md`:

| | structure | fixed |
|---|---|---|
| Чанки, що перетинають межу розділу | 0 | 80 з 89 (90%) |
| Таблиці, розрізані між чанками | 0 з 15 | 12 з 15 |

Вплив на якість пошуку (recall@k, MRR для обох стратегій) — у `REPORT.md`.

## Пошук
- **Embeddings**: `paraphrase-multilingual-MiniLM-L12-v2` локально через fastembed (ONNX, CPU, без ключа; кеш embeddings за хешем тексту).
- **Векторна база**: FAISS `IndexFlatIP` (косинус), payload-метадані поруч.
- **Лексичний**: BM25 (власна реалізація; для української — обрізання слів до 6 символів як простий стемінг).
- **Hybrid**: Reciprocal Rank Fusion (k=60) топ-30 з кожного пошуку.
- **Reranking**: cross-encoder `jina-reranker-v2-base-multilingual` на топ-20 (ліцензія CC-BY-NC — ок для навчального проєкту).
- **Фільтри за метаданими** (пре-фільтр): `status=current` (скасовані версії не шукаються), `access` за роллю
  (інженер NOC не бачить документів менеджменту), `date_from/date_to`, `doc_type`.

## RAG
- Контекст — у межах **бюджету токенів** (`rag.context_budget_tokens`); що не вмістилось — логуються.
- Відповідь — structured output: `not_found`, `answer`, `claims[{text, sources:[S1..]}]`.
  Посилання на неіснуючі джерела відкидаються; кожна цитата → документ, розділ, версія, файл.
- «Не знаю» на трьох рівнях: немає чанків після фільтрів → без LLM; (опц.) низький reranker score → без LLM; `not_found` від моделі.
- Промпти — `prompts/` з версіями і `CHANGELOG.md`.

## Evals (`evals/`)
- `testset.jsonl` — **26 питань**: 22 з відповіддю (факти, multi-hop, пастки зі скасованими версіями й схожими документами,
  фільтр доступу) і 4 без відповіді (поза корпусом, «дотичні», недоступні для ролі). Для кожного: еталон, ключові факти,
  очікувані джерела, evidence-фраза для retrieval, заборонені (застарілі) значення. Поле `reviewed` — ручна перевірка.
- **Retrieval**: recall@1/3/5, MRR@10 для bm25 / vector / hybrid / hybrid+rerank × structure / fixed, + ефект фільтрів.
- **Відповіді**: детерміновані (ключові факти, правильне джерело, «не знаю» де треба, застарілі значення, валідність цитат),
  LLM-as-a-judge (коректність vs еталон), faithfulness (кожне твердження vs контекст).
- **Калібрування судді**: `make label` → вручну `human_verdict` для ≥10 відповідей → `make calibrate` (згода, Cohen's κ, розбіжності).
- **CI**: `.github/workflows/evals.yml` на кожен push/PR; пороги — `config.yaml → eval.thresholds`; нижче порогу — job падає.
  Для LLM-частини додайте секрет: *Settings → Secrets and variables → Actions → New repository secret* `GEMINI_API_KEY`.

## Ablation (порівняння з погіршеною конфігурацією)
`config_ablation.yaml` — та сама система без BM25 і reranker (лише векторний пошук, top-3) і без фільтра `status`.
Запуск: `python main.py eval --config config_ablation.yaml` → `evals/results_ablation/`.
Показує, що метрики чутливі до якості пошуку; ручна розмітка для калібрування судді — `evals/human_labels.jsonl`
(скрипт розмітки — `tools/label.py`). Помилки порогів у ablation очікувані.
